# Bender: the usable internal-radio Wi-Fi toolkit

Product direction confirmed November 14, 2026: make the OnePlus 13's demonstrated internal-radio capability easy to install, understand and use in a complete local Wi-Fi assessment workflow. A usable product is the contribution to pursue. Publication priority does not depend on proving a first-ever attack or discovering a new vulnerability.

The proposed release promise is: **Install Bender on a supported rooted OnePlus 13, scan nearby networks, select a network or observed client, run supported assessments, and keep the evidence and results together—all using the internal Wi-Fi chipset.** This describes the release objective, not the capabilities of the current research APK.

Use the existing Kotlin/Compose Bender app as the product foundation. Reuse and qualify the proven managed-interface backend from the existing work. Preserve the Hijacker research/evidence tree and its current modifications. Maintain one capability engine rather than growing independent implementations for each interface.

There is a practical distribution gap worth pursuing: the [Kali wireless-card guide](https://www.kali.org/docs/nethunter/wireless-cards/), last updated June 16, 2025, labels QCACLD-3.0 support as monitor-only. That table explains some discoverability problems; it is not an exhaustive inventory of newer community work. Credit upstream tools and related projects. The headline can describe the complete product without asserting historical priority.

The install target is **root plus guided app setup**, with the app handling the remaining supported dependencies. The current NetHunter prerequisite is a concrete gap to close. A standalone runtime package needs versioned manifests, source/license notices, integrity verification, adequate-space checks, atomic staging, interrupted-install recovery and clean removal. Select the minimum runtime after auditing actual executable/library needs; do not solve usability by silently replacing an existing chroot or downloading an unpinned root script. Setup downloads occur before the optional lab IP-blocking profile is enabled; assessment and stored work remain local.

The most important hardware dependency is the capture/transmit transition. Existing capture and managed transmission are sequential. A reconnection handshake may occur before capture resumes. Measure that gap before advertising a reliable deauth-and-capture workflow. Passive capture of an ordinary controlled reconnection is independently useful and must work even if simultaneous capture/transmit remains unavailable. The product must explain this in the action's result, not report an empty capture as a successful handshake acquisition.

Deliver in this order:

1. **Setup and first successful scan.** Qualify the current APK, make dependency failures actionable, and remove the need for author-specific staging. Build the runtime installer against those measured prerequisites.
2. **A complete network workspace.** Scan, open a dossier, capture, stop, inspect and reopen the saved session. Make evidence persistence and recovery reliable before expanding the action list.
3. **The internal-radio demonstration.** Run the qualified directed request from the app and show the independently observed result. Test the capture transition and ordinary reconnect capture separately.
4. **A usable WPA2 assessment.** Qualify exchange analysis and audit input, implement the bounded audit workflow, and save verified results to the vault.
5. **Expand the supported catalog.** WPS, controlled AP experiments and other operations earn working actions through actual hardware results. PMF counters, dual STA, spectral/CFR and firmware work are scheduled when they unlock a user-facing capability or resolve a concrete defect.

The public-release demonstration should start from installation and finish with a saved, reopenable network assessment and restored connectivity. It should require no hidden terminal preparation. Record the exact supported build, APK/runtime hashes, root prerequisites, successful actions, limitations and failed controls. Have someone other than the author follow the guide on a supported device before describing the installation as easy. A single polished workflow that passes these checks is the first milestone; the broader tool catalog remains the continuing product scope.

Current starting points: `app/src/main/java/dev/sir/benderwifi/ui/LabApp.kt` (screens/actions), `data/LabDatabase.kt` and `data/LabRepository.kt` under that same package root (inventory/history), `runtime/catalog.json` (capabilities), `runtime/qca-runner.sh` and `runtime/qca-backend.py` (radio/runtime), and `engine/bender_engine/analysis.py` (protocol observations). Existing validation is in `VALIDATION.md`; it does not substitute for exact-handset release qualification.

This document changes release priorities only. No new installer, WPA workflow or radio capability was implemented or tested by writing it.
